## 1. Summary and goals

An open-source, offline-first Android music player that plays local files and downloads, streams from pluggable sources, and pairs with Nuclear on the PC. No backend, no account, no tracking. It fills the one gap Nuclear does not cover: there is no Nuclear app for phones, only a LAN browser remote.

Goals for v1:

- Plays reliably in the background with notification, lock-screen and Bluetooth controls.
- The whole library works with zero network: local files plus downloaded tracks.
- Pairs with desktop Nuclear: remote-control the PC player and import its playlists and favorites.
- Sources are plugins behind one interface, so a risky source can be left out of a build without touching the app.

Success targets (confirm during M1):

- Cold start under 2 s on a mid-range phone.
- Library scan of 2,000 tracks under 30 s.
- 1 h of screen-off playback with no stop or skip.
- 7 days of personal daily use with zero crashes before the first public release.

## 2. Scope v1 and non-goals

| Area | In v1 | Out of v1 |
| --- | --- | --- |
| Library | Scan chosen folders; MP3, FLAC, M4A/AAC, OGG, OPUS; tags and embedded artwork | Cloud libraries, tag editing |
| Playback | Queue, shuffle, repeat, gapless, background playback, media notification, Bluetooth and lock-screen controls, sleep timer | Equalizer, crossfade, Chromecast/DLNA, Android Auto |
| Collections | Playlists, favorites (tracks, albums, artists), listening history; JSON import/export | Smart playlists, recommendations |
| Sources | Provider interface; Local, Internet Archive | Jamendo (deferred), running Nuclear's JS plugins unchanged |
| Offline | Download a track, album or playlist from a provider; storage limit and cleanup | Background sync of new releases |
| Nuclear pairing | Remote-control the PC player; import playlists and favorites from the PC | Two-way live sync, playing PC audio on the phone |
| UI | English; light and dark themes | Translations, custom theme editor |

Non-goals for v1: iOS, a Play Store listing, any server or account, lyrics, scrobbling.

## 3. Architecture

One Expo app plus one small Kotlin module. Data flows one way: UI → state → services. Only the providers and the Nuclear link touch the network.

```text
UI (expo-router screens: library, search, now playing, playlists, downloads, PC remote)
  └─> State (Zustand: player, library, settings; rebuilt from SQLite on start)
        ├─> Player        expo-audio playlist, gapless, media controls ──> Android media session / foreground service
        ├─> Library scan  Kotlin Expo module over Android MediaStore ──> SQLite
        ├─> Downloads     expo-file-system, resume, storage limit    ──> SQLite
        ├─> Providers     local, archive (youtube: full only, v1.1) ──HTTPS──> Internet Archive
        └─> Nuclear link  Jam API client, LAN discovery, SSE           ──HTTP/SSE──> Nuclear on the PC (port 4120–4129)
SQLite (expo-sqlite): tracks, playlists, favorites, downloads, history, pairings, kv
```

Stack:

- Expo SDK 58 (React Native 0.88), TypeScript strict, expo-router. Dev client with `npx expo run:android`; release with local `gradlew assembleRelease`. No Expo Go; EAS only as a fallback. Continuous Native Generation: `android/` is generated by `npx expo prebuild` and not committed.
- Audio: expo-audio `AudioPlaylist` for the queue and gapless playback. `setActiveForLockScreen` keeps the media foreground service alive; without it Android stops audio after about 3 minutes in the background. Config plugin option `enableBackgroundPlayback: true`. Gapless on Android is verified in M1.
- Not react-native-track-player: v5 needs a paid licence for freelancers and revenue apps; v4 is frozen.
- Library: a local Expo module in Kotlin reads `MediaStore.Audio` (title, artist, album, album artist, track number, duration, size, date modified, album id) in one query, because expo-media-library does not expose tags.
- Storage: expo-sqlite with hand-written forward migrations behind a small `Db` interface, so tests run on better-sqlite3 in Node.
- Network: `fetch` for providers and the Jam API; an SSE client for `/api/events` (evaluate react-native-sse in M3).
- Tests: Jest (jest-expo) with React Native Testing Library; Maestro flows on a real device.

Module layout:

```text
app/                  expo-router screens
src/
  db/                 Db interface, migrations, queries
  stores/             zustand: player, library, settings
  player/             expo-audio wrapper, queue, play counter
  library/            scanner service, artwork cache
  providers/          SourceProvider interface; local, archive
  providers-youtube/  full flavour only; excluded from clean builds at bundle time (v1.1)
  downloads/          queue, resume, storage limit
  nuclear/            Jam API client, SSE, pairing
  i18n/               en
modules/media-store/  Kotlin Expo module over MediaStore
```

## 4. Music sources

```ts
interface SourceProvider {
  id: string; // 'local' | 'archive' | 'jamendo' | 'youtube'
  capabilities: Array<'search' | 'stream' | 'download' | 'albums' | 'artists'>;
  search(q: string, opts: { types: SearchType[]; limit: number }): Promise<SearchResult>;
  resolveStream(ref: ProviderRef): Promise<{ url: string; mime: string; expiresAt?: number }>;
  download?(ref: ProviderRef, dest: string, onProgress: (p: number) => void): Promise<LocalFile>;
}
```

| Provider | Build | What it gives | Key / limit | Licence of content |
| --- | --- | --- | --- | --- |
| Local files | All | The device library, fully offline | None | The user's own files |
| Internet Archive | All | Search, stream, download of public audio collections | No key | Mostly public domain or CC; per item |
| Jamendo (deferred, not in v1) | — | Search, stream, download of independent music | `client_id`; non-commercial tier 35,000 requests/month, so each user would enter their own key | CC licences, per track |
| YouTube (youtubei.js, MIT) | `full` only (v1.1) | Search and stream; download | None; breaks when YouTube changes | Copyrighted; against YouTube's terms |

Not in v1: SoundCloud (API keys need a paid Artist Pro subscription), Spotify (no audio access for third-party players). NewPipeExtractor (GPL-3.0, Java) is not used.

## 5. Desktop sync with Nuclear

Nuclear Jam's HTTP API binds to `0.0.0.0` on ports 4120–4129 (reachable over LAN and Tailscale) and has no authentication. Remote control needs no change to Nuclear.

| Feature | Endpoint(s) | Works today |
| --- | --- | --- |
| Pair by LAN discovery or manual host | probe `/api/health` on ports 4120–4129 | Yes |
| Live now-playing and queue | `GET /api/events` (SSE: `queue`, `playback`, `settings`) | Yes |
| Play, pause, next, previous, seek, volume, shuffle, repeat | `POST /api/playback/*` | Yes |
| Search on the PC and send tracks to its queue | `POST /api/search`, `POST /api/queue/add` | Yes |
| Favorite the PC's current track | `POST /api/favorites/tracks/add` | Yes |
| Lyrics of the PC's current track | `GET /api/lyrics/current` | Yes |
| Import the PC's playlists and favorites | No read endpoint exists | No |

v1 import path: Nuclear exports playlists as JSON; the phone imports those files via the share sheet or file picker. Track refs are re-resolved through the matching provider; unresolved items stay marked "not available offline". Imports are one-way and additive; a re-import updates the playlist with the same Nuclear id and never deletes phone-only items.

No upstream PR: Nuclear does not accept code contributions. Reading the PC's playlists and favorites directly is evaluated in M3 as an "Aulos Link" Nuclear plugin that would use the existing Jam settings endpoints as a mailbox (spike only).

Reference: nukeop/nuclear `packages/docs/integrations/http-api.md`, `packages/player/src-tauri/src/http_api/mod.rs` at commit `5221018` (2026-10-22).

## 6. Data model

One SQLite database holds everything durable; Zustand holds only UI and player state. A track is one row whether local, downloaded or streamed, keyed by `(provider, provider_ref)`.

| Table | Key columns | Purpose |
| --- | --- | --- |
| `tracks` | `id` PK, `provider`, `provider_ref` (unique pair), `title`, `artist`, `album`, `album_artist`, `track_no`, `disc_no`, `duration_ms`, `artwork_uri`, `local_path` (null if not on device), `file_mtime`, `file_size` | Every playable track |
| `tracks_fts` | FTS5 over `title`, `artist`, `album` | Instant offline search |
| `playlists` | `id` PK, `name`, `nuclear_id` (unique, nullable), `created_at`, `updated_at` | User and imported playlists |
| `playlist_items` | (`playlist_id`, `position`) PK, `track_id` | Ordered playlist contents |
| `favorites` | (`kind`, `key`) PK, `added_at`; `kind` = track, album or artist | Favorites |
| `downloads` | `track_id` PK, `status`, `bytes_done`, `bytes_total`, `error`, `updated_at` | Download queue and resume |
| `history` | `id` PK, `track_id`, `played_at`, `ms_played` | A play counts after 30 s or half the track |
| `pairings` | `id` PK, `name`, `base_url`, `last_seen_at` | Paired Nuclear desktops |
| `kv` | `key` PK, `value` (JSON) | Settings |
| `http_cache` | `key` PK (provider + normalised request), `body` (JSON), `fetched_at`, `ttl_s` | Provider response cache (M2) |
| `schema_migrations` | `version` PK, `applied_at` | Forward-only migrations |

Albums and artists are SQL views over `tracks`. Remote tracks (M2) also store `license_url` and `attribution`, and are written to `tracks` only when the user queues, saves, favourites or downloads them, not for every search result. Nothing secret ships in the APK or the repo.

## 7. Licensing, distribution and risks

The app copies no Nuclear code (it only calls Nuclear's HTTP API), so AGPL does not apply. Licence: GPL-3.0-or-later. All planned dependencies are permissive (expo-audio MIT, youtubei.js MIT); check every new dependency's licence for GPL-3.0 compatibility.

| Flavour | Providers | Channel | Signing |
| --- | --- | --- | --- |
| `clean` | Local, Internet Archive | GitHub Releases, F-Droid; Play Store possible later | Own release keystore, kept outside the repo with an offline backup |
| `full` (v1.1) | `clean` + YouTube | GitHub Releases only (F-Droid only with the NonFreeNet anti-feature) | Same keystore, `applicationId` `com.anywecon.aulos.full` |

Every release ships the APK and its SHA-256 checksum, built locally with `gradlew assembleRelease`.

| Risk | Impact | Mitigation |
| --- | --- | --- |
| YouTube changes break the extractor | `full` stops streaming until updated | Isolated provider; `clean` unaffected |
| YouTube terms / takedown requests | Repo or release takedown | YouTube provider in its own repo |
| Play copyright policy bans unauthorised download apps | `full` can never be listed | Only `clean` is a store candidate |
| Jam API has no authentication | Anyone on the same network controls the PC player | Warn in pairing UI; Windows firewall: allow Nuclear on Private networks only; turn Jam off on public Wi-Fi |
| Cleartext HTTP to the PC | LAN traffic to Jam is unencrypted | App-level guard allows HTTP only to private-network hosts; Tailscale encrypts remote use |
| OEM battery killers stop background audio | Playback stops with screen off | Media foreground service via lock-screen controls; one-time battery-optimisation prompt |
| Play personal accounts need 12 testers for 14 days | Delay before a `clean` listing | Not needed for v1; recheck rule before any store plan |
